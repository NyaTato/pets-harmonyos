# 面试讲解提纲

## 约 1 分钟介绍

“宠缘是我独立开发的 HarmonyOS 宠物领养交互原型，使用 ArkTS、ArkUI 和 Stage 模型。我把页面、组件、路由、状态和 Mock 数据分开组织，完成了从宠物浏览、详情到领养申请等主要演示路径。开发中我重点处理了收藏数据在详情页与收藏列表之间不一致的问题，让两处读取同一份按用户区分的内存记录，并补充了可执行测试（29/29 通过）。2026-10-15 我在 OpenHarmony 6.0.2.130 模拟器上安装未签名 HAP，复测了首页、列表、详情、收藏/取消、我的收藏、领养申请、社区和个人中心，收藏计数 2→1→2 通过，申请提交后新增第 4 条 Mock 记录。项目目前仍是原型：没有真实后端与服务端持久化，推荐展示、AR 预览和走失预警是模拟页面，没有真实模型、AR 引擎或设备。我也清理了无授权图片，保留自绘占位资源，并把模拟器与物理真机、跨重启持久化的边界清楚列出。”

## 可能的问题与回答思路

1. **为何选择 Stage 模型，入口如何到首页？** 从 `entry/src/main/module.json5` 的 `mainElement` 讲到 `EntryAbility` 加载 `pages/Splash`，再到 `RouterHelper` 与 `MainTab`；不要推断尚未验证的启动时延。
2. **收藏为什么会不同步，怎样避免？** 原详情页只改局部 `isFavorite`，收藏页读取 `InteractionData`；改为按用户和宠物 ID 查询、更新同一记录，进入或返回页面时重新读取。说明该记录仅存内存，未跨重启持久化。
3. **`ApiService` 是否已经接后端？** 没有。它包装 Mock 函数并模拟等待；真实后端需要认证、接口错误、重试和数据持久化设计。不要称作线上 API。
4. **推荐、AR 和 IoT 哪些是真的？** 推荐服务有本地规则打分，但演示页还包含随机展示；AR 是图片交互，不是相机/空间锚定；预警是本地模拟位置，不是电子围栏。可解释未来接入所需的 SDK、权限与测试。
5. **如何证明代码质量与可公开性？** 展示收藏记录的可执行测试（29/29）、差异检查、Mock 边界文档和素材替换；说明 ArkTS 已成功编译为未签名 HAP（仍有 ArkTS 警告），并于 2026-10-15 在 OpenHarmony 6.0.2.130 模拟器上安装启动复测；Node 测试不能冒充设备验收，编译成功不代表物理真机通过，申请和收藏均为内存 Mock。

讨论时可直接打开 [`architecture.md`](architecture.md) 的结构图，并准备展示九张真实模拟器截图（01–09）；其中 `06-adoption-form-emulator.png` 是表单初始画面，`09-my-apply-emulator.png` 是提交后列表，没有成功提示截图；不使用网页原型图代替，不冒充真机。
